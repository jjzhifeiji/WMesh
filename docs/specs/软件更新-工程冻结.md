# 软件更新工程冻结

> 业务对错以 `docs/specs/软件更新.md` 和 `软件更新-验收矩阵.md` 为准。  
> 本文件只冻结怎么落地；不改必须确认才装、只向前、Client 永不连 WAN、库不单独发包。  
> 不新建 Client 工程、不测 MQTT、不向 Robot 下指令、不接系统 APK 安装器。  
> `go test` 不连真 Docker、不重启进程；updater 用空实现或夹具回写结果。

---

## 1. 目录与构建

- 工程仍只有 `global/` 与 `factory/`。域文件：`store/update.go`、`service/update.go`、`httpapi/update.go`。
- 厂服务包和 APK 发布都发 MQTT `software` 小指令（种类、版本、版本名），**不含正文**。本厂已有完整副本或同版本正在拉则跳过。**不再**要 `softwaresign`、每厂分发、每机就绪信封。
- 摘要用本轮 `digest` 的 SHA-256。包字节进本侧 `blob.Store`（测试用内存）；**不进** `assets`，不走内容租约/WM2。
- 云端/厂服务包是 **只含 app** 的 Docker 镜像 tar（API、管理台、已 embed 的 Flyway）。首次装机仍用现有全量 `make bundle`。
- 两边 `docker-compose.yml` 各加一个 **updater** 服务：不随业务 app 一起换掉；挂 docker.sock 和更新目录。**app 不挂 docker.sock，不以 root 自换。**
- 迁库仍是两边 `internal/platform/migrate`：进程内 Flyway，禁止 down。WAN 启动迁 WAN 库；厂侧打开各厂库时迁。
- 本地发布：`make test` 通过后，按种类 `docker save` 对应 app 镜像或打 APK；三种包分开发。

## 2. 库

只向前加迁移，禁止改写已落库发布原文与审计。已有 `0018` / `0024` 不动。

WAN 新迁移：

- `software_releases.kind` 放宽为 `wan_service` / `factory_service` / `client_apk`。
- 新增 `software_state`：按种类一行，先记 `wan_service` 已装版本；未装为 0。
- `software_distributions`、`wan_signing_keys` **不再写入**；本圈不删表、不改历史行。

厂新迁移：

- `software_replicas` 仍主键 `(kind, version)`，种类仍是 `factory_service` / `client_apk`。新拉入的副本不再写签名；旧签名列可空，禁止改已收行的摘要。
- `software_state` 仍只记 `factory_service`。客户端已装版本只在本机袋。
- `wan_trust` 不再用于软件包。

仍不准出现他厂包、厂内人员明细进 WAN、把软件包插入 `assets`。

## 3. 元数据（无签名信封）

两边同名字段（不共用包）：

| 字段 | 含义 |
| --- | --- |
| `kind` / `version` / `versionName` | 种类、该种类单调整数、给人看的版本名 |
| `digest` | 包文件 SHA-256 |
| `body` | 仅拉取接口返回；列表与弹窗不带字节 |

低版本：该种类已有更高**已发布、已拉到或已安装**版本 → `revision is not strictly newer`。同版本同摘要再来 → 幂等。同版本不同摘要 → `integrity`。

## 4. 许可落点

| 谁 | 入口 |
| --- | --- |
| WAN 管理员 | `PublishSoftware`、`ListSoftwareReleases`、`DeleteSoftware`、`PruneSoftware`、`StorageUsage`、`RequestImagePrune`、`PendingWANSoftware`、`ConfirmWANUpdate`（仅 `wan_service`） |
| 已认领厂会话 | `LatestSoftware`、`PullSoftware`（仅 `factory_service` / `client_apk`） |
| 本厂超管 | `ListFactorySoftware`、`DeleteFactorySoftware`、`PruneFactorySoftware`、`StorageUsage`、`RequestImagePrune`、`SyncFactorySoftware`、`PendingFactorySoftware`、`ConfirmFactoryUpdate`（仅 `factory_service`） |
| 本机袋当前登录者 | `PadClientSoftware`、`PullPadClientSoftware`、`ConfirmClientUpdate`（仅 `client_apk`） |

服务层确认**只写待切换记录和盘上 tar**，不调 Docker。updater 落地成功并探活通过后，才由服务写入 `software_state` 或袋内版本。失败保持旧版本，夹具可回写失败。

`ConfirmClientUpdate`：未登录、焊接中、节点凭证不允许新开、低版本、摘要不对 → 拒绝。不再验厂签就绪信封。

厂拉包走已有厂→WAN HTTPS 证明（与通道拉正文同一套身份头），不走人员 cookie。平板拉 APK 走本厂人员会话。

服务层无：`DistributeSoftware`、`AcceptSoftwareDelivery`、`ReadyClientUpdate`、静默安装、下发旧版回滚、Client 拉 WAN、把软件包写入 `assets`。

## 5. updater

- 只认更新目录里「已确认、摘要已核」的 app tar。
- `docker load` 后给新镜像打待切标签；把正在跑的 app 镜像标成 `previous`；`compose up` **只重建 app**。
- 探活失败或启动迁库失败：把 app 切回 `previous`，写失败状态；不碰 db / oss / alloy。
- 成功写就绪状态；app 读到后记已装。
- 清镜像：更新目录里放请求，updater 只清无用 app 镜像和悬空层，保留 current / previous 和基础设施镜像。无论成败都写 `prune.json`；周期写 `images.json`（种类、去重个数、去重字节、标签列表）。已落下的 pending 不挡清理。
- 测试默认空 updater：确认只留下待切换，不标已装，除非夹具宣称落地成功。

## 6. 迁移与验收

- 新 SQL：WAN / 厂各一条只向前迁移（放宽 kind、WAN 的 `software_state`、副本签名可空）。历史表 `flyway_schema_history`。
- 每张新表、每个新列 `COMMENT ON`。禁止改已落库发布摘要与审计原文。
- `go test` 不依赖真 OSS、不重启进程、不连真 Docker。
- 通道索引仍不含软件；厂服务包和 APK 靠发布时下行 `software`，回连和定时再问最高版补拉。提示与确认不读 WAN 包。

## 7. 本圈完成定义

三种包独立发布、厂服务包和 APK 用 MQTT 通知厂端静默拉、检查更新只认本地完整包、确认只落盘、updater 只换 app、Flyway 跟镜像、只向前、无软件签名/无包正文进 MQTT，且能支撑新矩阵。未验证不得当完成物。
